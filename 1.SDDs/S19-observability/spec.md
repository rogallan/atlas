# Spec — S19 · Observability

> **Domain:** Operations & Observability · **Quarter:** Q3 · **Depends on:** S01 (Python Toolchain), S03 (FastAPI Gateway), S04 (Ollama Provider), S14 (Agent Graph)

## 1. Goal

Implement an enterprise-grade observability framework for the ATLAS banking copilot, providing end-to-end distributed tracing with Correlation IDs across sessions, structured JSON logging, stage-by-stage latency tracking (Gateway -> Intent Router -> RAG / MCP -> Validator -> Response), token accounting with cost estimations, and operational metrics dashboards.

## 2. Context

Per `architecture.md` and `PDI_ATLAS_GenAI_Banking_Copilot_PT_BR.html`, understanding where an agentic application spends execution time and tokens is essential for production operations. A single relationship manager interaction traverses multiple boundaries: FastAPI Gateway, Ollama inference for routing, Vector Store retrieval, typed MCP tool calls, and post-validation. S19 equips ATLAS with full visibility: tracing requests from the moment they leave React Chat, through ngrok and the Agent Graph, down to individual tool executions and back.

## 3. In scope

- Correlation & Session ID propagation across all asynchronous boundaries (`X-Correlation-ID`, `X-Session-ID`).
- Structured JSON logging with standardized schema (timestamps, log levels, correlation ID, component name, sanitized payloads).
- Distributed tracing using OpenTelemetry (OTel) standards, capturing spans for:
  - Gateway HTTP request handling.
  - S05 Intent Router classification.
  - S07 RAG vector search and synthesis.
  - S08–S13 MCP tool execution.
  - S14 Validator/Critic inspection.
- Metric collectors:
  - Per-stage latency (p50, p95, p99).
  - Token consumption tracking (prompt tokens, completion tokens, total tokens per turn).
  - Synthetic cost modeling (tracking estimated cost if running on commercial models vs. local GPU/CPU compute time).
  - Error and fallback rates.
- Observability export & visualization:
  - Local export to stdout and file-based rotation.
  - Support for Prometheus metrics export (`/metrics`) and OTLP trace exporter (ready for Jaeger, Grafana Tempo, or AWS CloudWatch in S21).

## 4. Out of scope

- Setting up production cloud monitoring infrastructure on AWS (covered in S21 Terraform AWS).
- Continuous evaluation scorecards and golden dataset regression tracking (covered in S17 Harness / Evals).
- Application performance monitoring (APM) agent injection for the external Vercel React frontend.

## 5. Requirements

- **R1. Ubiquitous Correlation ID:** Every request must generate or accept an `X-Correlation-ID` header at the Gateway boundary and propagate it through all downstream logs, traces, and tool calls.
- **R2. Structured JSON Logging:** Application logs must be emitted as machine-parsable JSON lines conforming to a documented schema (`timestamp`, `level`, `correlation_id`, `session_id`, `component`, `message`, `metadata`), with automatic PII masking (S18).
- **R3. Granular OpenTelemetry Spans:** Every critical phase of the Agent Graph must be instrumented with an individual trace span recording duration, status, and execution metadata (e.g. number of retrieved chunks, tool name called, intent classified).
- **R4. Token Accounting:** The Ollama provider and agent orchestrator must extract and record token usage per interaction (`prompt_eval_count`, `eval_count`) and aggregate totals per session.
- **R5. Latency & Performance Breakdown:** The system must record and expose duration breakdown per step, enabling operators to identify bottlenecks (e.g. LLM generation latency vs. vector search time).
- **R6. Metrics Endpoint:** Expose a standard `/metrics` endpoint compatible with Prometheus, reporting request counts, error rates, token counters, and latency histograms.

## 6. Acceptance criteria

- 100% of logs and trace spans generated by a chat request share the identical `correlation_id`.
- An end-to-end trace view visibly displays individual spans for Router, RAG/MCP, and Validator with accurate duration timings.
- Token counts (prompt, completion, total) are accurately logged and aggregated per conversation session.
- `GET /metrics` returns valid Prometheus-formatted metrics without exposing internal secrets.
- Automated tests verify trace context propagation across async tasks and ensure zero unhandled logging exceptions.
